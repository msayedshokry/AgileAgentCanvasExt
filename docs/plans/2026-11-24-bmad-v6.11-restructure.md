# Plan: Adopting BMAD v6.11's skill restructure

**Date:** 2026-11-24
**Status:** Draft, awaiting approval
**Baseline:** Extension skills are at BMAD v6.9.0. The v6.10 to v6.12.4 review and prompt-quality changes were ported on 2026-11-24 (see `CHANGELOG.md` › Unreleased). This plan covers only the **structural** part of v6.11, which that port left out.

## 1. What upstream changed

| Upstream v6.11 change | Old IDs (ours) | New upstream ID | Upstream fate of old ID |
|---|---|---|---|
| Quick Dev renamed to Build, the one official Phase 4 loop | `aac-quick-dev` | `bmad-build` | forwarding shim |
| Unattended single-iteration worker | (none; our closest is `aac-kanban-dev-executor`) | `bmad-build-auto` | new |
| Story pair deprecated | `aac-create-story`, `aac-dev-story` | `bmad-build` (by spec + story id) | shim, removed at v7 |
| Readiness folded into planning | `aac-check-implementation-readiness` | `bmad-sprint-planning` readiness gate | removed |
| Status view folded into planning | `aac-sprint-status` | `bmad-sprint-planning action=status` | shim |
| Reviews and editorial merged into lenses | `aac-review-adversarial-general`, `aac-review-edge-case-hunter`, `aac-editorial-review-prose`, `aac-editorial-review-structure` (+ our new `aac-review-verification-gap`) | `bmad-review` with `[[workflow.lenses]]` | shims |
| Research trio merged | `aac-market-research`, `aac-domain-research`, `aac-technical-research` | `bmad-deep-recon` (6 type packs, 3 modes) | shims |
| Project docs replaced by one `AGENTS.md` block | `aac-document-project`, `aac-generate-project-context` | `bmad-project-context` | shims |
| Removed outright | `aac-index-docs`, `aac-shard-doc` | none | removed |
| Retired earlier (v6.10) | `aac-investigate` | none | removed |
| Renamed (v6.12) | `aac-checkpoint-preview` | `bmad-walkthrough` | shim |
| Tech writer persona retired | `aac-agent-tech-writer` (persona in `src/`) | optional agent "coming soon" | removed |
| Planning→execution contract | none | `stories.yaml` beside `SPEC.md`, `[workflow] implementation_handoff` | new |
| Evidence-based retro, deterministic sprint script | `aac-retrospective`, `aac-sprint-planning` | same IDs, rebuilt | in place |

Upstream infrastructure that does **not** apply to us: the layered TOML config and `render_skill.py` snapshots, the `uv` requirement, the installer and shims-opt-in flags. We ship skills inside the VSIX and resolve them through our own catalogue.

The canvas Story card and the kanban lanes assume the **create-story → dev-story → code-review** chain and story files under `implementation_artifacts`. That assumption is the real migration cost, not the renames.

## 3. Options

**A. Full adopt.** Rename everything to upstream's shape, delete the old skills, and re-plumb the canvas onto spec folders plus `stories.yaml`. This tracks upstream most closely, but it breaks every user's existing story files and customizations at once. It is also the shape v7 will change again.

**B. Bridge (recommended).** Add the new capabilities as new `aac-*` skills. Turn the old IDs into thin forwarding shims, as upstream did. Route every `src/` reference through a single alias map so later renames are one-line changes. Leave the canvas story chain alone until v7's shape is known.

**C. Skip.** Stay on the v6.9 structure and keep porting prompt-quality fixes only. This costs nothing now, but the catalogue keeps drifting and the next sync costs more.

## 4. Plan for option B

### Phase 1: Alias seam (S, no behavior change)
- Add `src/state/skill-aliases.ts`, a `Record<legacyId, currentId>` plus `resolveSkillId()`.
- Replace the hard-coded IDs in the 10 files above with `resolveSkillId(...)` or the constant.
- Test: a Cucumber scenario asserting that every alias target exists under `resources/_aac/skills/`.

### Phase 2: Additive new skills (M)
- `aac-deep-recon`: port upstream with its three modes and six type packs. Turn `aac-market/domain/technical-research` into shims that forward with `type` pre-set.
- `aac-project-context`: port upstream (`setup`/`refresh`/`record`/`audit` writing an `AGENTS.md` block). Keep `aac-generate-project-context` and `aac-document-project` working; their `project-context.md` is still read as a source. **Decision needed:** should canvas features that read `project-context.md` keep it as the primary source?
- `aac-review`: one skill with lenses (`adversarial`, `edge-case-hunter`, `verification-gap`, `structure`, `prose`). Keep the existing reviewer skills as the lens bodies. The code-review layers keep invoking them directly, which upstream also reverted to in v6.11 (#2638).
- `aac-walkthrough`: rename `aac-checkpoint-preview` and add a shim.

### Phase 3: Build as the dev path (M–L)
- `aac-build`: port upstream `bmad-build` on top of our `aac-quick-dev` (already its v6.9 ancestor). Make `aac-quick-dev` a shim.
- Map `aac-build-auto` onto `aac-kanban-dev-executor`. Adopt its spec-frontmatter state machine, `deferred:` list, and `implementation_handoff` key, so the kanban can dispatch to any harness without forking the skill. This fits the multi-harness design from 0.6.0.
- Keep `aac-create-story` and `aac-dev-story` fully working, but drop them from `aac-help` recommendations.

### Phase 4: Planning and retro rebuild (M)
- Fold the readiness gate into `aac-sprint-planning`, and turn `aac-check-implementation-readiness` and `aac-sprint-status` into shims.
- Port the evidence-based `aac-retrospective` (it is 1,519 lines today; upstream is a few hundred plus references).
- `sprint_plan.py`: **decision needed.** It requires Python/`uv` on the user's machine. The alternative is a TypeScript port inside the extension, which the canvas could also call directly.

### Phase 5: Removals (S, gated on user decision)
- `aac-investigate`, `aac-index-docs`, `aac-shard-doc`, and the tech-writer persona: decide whether to keep them as AAC-specific extras or remove them.

## 5. Decisions needed before execution

1. Choose an option (A, B or C).
2. Should `project-context.md` or `AGENTS.md` be the canonical project context for canvas features?
3. Should `sprint_plan.py` be Python (upstream parity) or a TypeScript port (no runtime dependency)?
4. Keep or remove `aac-investigate`, `aac-index-docs`, `aac-shard-doc`, and the tech-writer persona?
5. Target v6.12.4 now, or wait for v7 to leave preview? CIS and TEA are already pinned at their last v6 releases upstream.

## 6. Done when

- Every legacy ID resolves through `skill-aliases.ts`, and a test enforces that every target exists.
- `npm run test` and `npm run lint` pass, and `npm run compile` builds the VSIX.
- The canvas Story → Dev → Review flow works unchanged on an existing project (manual check in the Extension Development Host).
- A CHANGELOG entry lists each rename with its forwarding behavior.
